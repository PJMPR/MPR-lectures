1. Wstęp - czym są testy jednostkowe?

Test jednostkowy (unit test) to automatyczna procedura, która sprawdza, czy pojedyncza jednostka kodu (zazwyczaj metoda) zachowuje się zgodnie z oczekiwaniami.

Przykład:

Jeśli napiszemy metodę:

public int add(int a, int b) {
    return a + b;
}

To test jednostkowy sprawdzi:

  • add(2, 3) zwraca 5 ✅
  • add(-1, 1) zwraca 0 ✅
  • add(0, 0) zwraca 0 ✅

Kluczowe cechy testów jednostkowych:

  • Automatyczne - uruchamiają się bez interwencji człowieka
  • Szybkie - zwykle wykonywane w milisekundach
  • Niezależne - każdy test nie zależy od innych
  • Powtarzalne - zawsze dają ten sam wynik
  • Izolowane - testują konkretną funkcjonalność

2. Dlaczego testy są ważne?

Testy jednostkowe to fundamentalny element nowoczesnego tworzenia oprogramowania. Oto główne powody, dla których powinniśmy je pisać:

✅ Pewność w kodzie

Dzięki testom wiemy, że nasz kod działa jak powinien. Jeśli test przejdzie, funkcjonalność jest poprawna.

🛡️ Zapobieganie regresji

Gdy zmieniamy kod (refaktoryzujemy, optymalizujemy), testy sprawdzą, czy nie zepsuli​śmy czegoś, co wcześniej działało.

📖 Dokumentacja kodu

Testy pokazują, jak należy używać naszego kodu. Są to żywe przykłady zachowania się metod.

🔧 Ułatwienie refaktoryzacji

Możemy śmiało zmienić implementację, jeśli testy nadal przechodzą.

🐛 Szybsze łapanie błędów

Błędy są wykrywane w momencie ich wprowadzenia, a nie w produkcji.

💪 Zwiększenie jakości kodu

Kod testowany jest zazwyczaj lepiej zaprojektowany i łatwiej się go czyta.

3. AAA Pattern (Arrange, Act, Assert)

AAA Pattern to standardowa struktura pisania testów jednostkowych. Każdy test powinien mieć trzy fazy:

🔧 Arrange (Przygotowanie)

Przygotowujemy dane i obiekty potrzebne do testu. Tworzą "fixture" - stan początkowy testu.

▶️ Act (Akcja)

Wykonujemy metodę, którą testujemy. Wywołujemy kod, który chcemy sprawdzić.

✔️ Assert (Asercja)

Sprawdzamy wynik. Porównujemy rzeczywistą wartość z oczekiwaną.

Przykład AAA Pattern:

@Test
public void testAdd_PositiveNumbers() {
    // ARRANGE - przygotowanie
    int a = 5;
    int b = 3;
    Calculator calculator = new Calculator();
    
    // ACT - wykonanie
    int result = calculator.add(a, b);
    
    // ASSERT - sprawdzenie
    assertEquals(8, result, "5 + 3 powinno równać się 8");
}

Struktura AAA czyni testy:

  • Zrozumiałymi - łatwo zobaczyć co się testuje
  • Utrzymywalnymi - łatwo modyfikować i rozwijać
  • Odtwarzalnymi - zawsze mają ten sam format

4. JUnit 5 - Podstawy

JUnit 5 to najnowszy framework do testowania w Java. Jest nowoczesny, elastyczny i łatwy w użyciu.

📌 Anotacja @Test

Anotacja @Test oznacza, że metoda jest testem. JUnit automatycznie ją uruchomi. 

@Test
public void testAdd() {
    // To jest test
    assertEquals(5, calculator.add(2, 3));
}

🔄 @BeforeEach - Setup

Metoda oznaczona @BeforeEach uruchamia się przed każdym testem. Używamy jej do inicjalizacji "fixture". 

private Calculator calculator;

@BeforeEach
public void setUp() {
    // Ta metoda uruchamia się przed KAŻDYM testem
    calculator = new Calculator();
}

@Test
public void testAdd() {
    // calculator już jest utworzony
    assertEquals(5, calculator.add(2, 3));
}

@Test
public void testSubtract() {
    // calculator jest znowu świeży, nowo utworzony
    assertEquals(1, calculator.subtract(3, 2));
}

Dlaczego @BeforeEach? Aby każdy test otrzymywał czysty, niezmodyfikowany obiekt. Testy są wówczas niezależne od siebie.

🧹 @AfterEach - Teardown

Metoda oznaczona @AfterEach uruchamia się po każdym teście. Używamy jej do czyszczenia zasobów (np. zamykanie plików, połączeń do BD). 

@AfterEach
public void tearDown() {
    // Czyszczenie zasobów
    calculator = null;
}

📊 Porównanie: @BeforeEach vs @Before (JUnit 4)

JUnit 5 (@BeforeEach) JUnit 4 (@Before)
Nowoczesna Stara (legacy)
Wsparcie lambda Brak lambda
Bardziej elastyczna Mniej elastyczna

Na tym wykładzie używamy JUnit 5!

5. Asercje (Assertions)

Asercje to funkcje, które sprawdzają, czy warunek jest spełniony. Jeśli asercja nie przejdzie, test się nie powiedzie.

📋 Główne asercje JUnit 5

Asercja Znaczenie Przykład
assertEquals(expected, actual) Sprawdza równość wartości assertEquals(5, calculator.add(2, 3))
assertNotEquals(unexpected, actual) Sprawdza nierówność assertNotEquals(0, calculator.add(2, 3))
assertTrue(condition) Sprawdza czy warunek jest true assertTrue(calculator.isEven(4))
assertFalse(condition) Sprawdza czy warunek jest false assertFalse(calculator.isEven(3))
assertNull(object) Sprawdza czy obiekt to null assertNull(StringUtils.reverse(null))
assertNotNull(object) Sprawdza czy obiekt nie jest null assertNotNull(calculator)
assertThrows(ExceptionClass.class, () -> ...) Sprawdza czy zostaje rzucony exception assertThrows(ArithmeticException.class, () -> calculator.divide(10, 0))

Przykłady asercji:

// assertEquals
@Test
public void testAdd() {
    assertEquals(8, calculator.add(5, 3), "5 + 3 powinno równać się 8");
}

// assertTrue / assertFalse
@Test
public void testIsEven() {
    assertTrue(calculator.isEven(4));      // 4 jest parzyste
    assertFalse(calculator.isEven(3));     // 3 nie jest parzyste
}

// assertNull / assertNotNull
@Test
public void testNullHandling() {
    assertNull(StringUtils.reverse(null));      // reverse(null) = null
    assertNotNull(StringUtils.reverse("hello")); // reverse("hello") ≠ null
}

Wskazówka: Zawsze dodaj wiadomość (message) do asercji! Pomaga w debugowaniu, gdy test się nie powiedzie.

6. Testowanie exceptionsów

Ważnym aspektem testowania jest sprawdzenie, czy kod rzuca właściwe exceptiony w odpowiednich sytuacjach.

assertThrows() - Sprawdzenie Exception

@Test
public void testDivide_ByZero_ThrowsException() {
    // Sprawdzamy, czy dzielenie przez 0 rzuca ArithmeticException
    assertThrows(ArithmeticException.class, () -> {
        calculator.divide(10, 0);
    });
}

assertThrows przyjmuje:

  • Klasę exceptiony, którą oczekujemy
  • Lambda wyrażenie, które ma rzucić exception

Bardziej szczegółowy test:

@Test
public void testDivide_ByZero_ExceptionDetails() {
    // Możemy sprawdzić szczegóły exceptiony
    ArithmeticException exception = assertThrows(
        ArithmeticException.class, 
        () -> calculator.divide(10, 0)
    );
    
    assertEquals("Cannot divide by zero!", exception.getMessage());
}

Edge cases z exceptionsami:

  • Dzielenie przez zero → ArithmeticException
  • Null input → NullPointerException
  • Ujemne wartości gdzie nie powinny być → IllegalArgumentException
  • Indeks poza tablicą → IndexOutOfBoundsException

7. Best Practices

📝 1. Nazewnictwo testów

Nazwa testu powinna jasno opisywać, co testuje. Popularna konwencja: 

test[MethodName]_When[Condition]_Then[ExpectedResult]
// ✅ DOBRE nazwy
testAdd_WhenPositiveNumbers_ThenReturnSum()
testDivide_WhenDivisorIsZero_ThenThrowException()
testIsEven_WhenNumberIs4_ThenReturnTrue()

// ❌ ŹLE nazwy
test1()
testMethod()
myTest()

🎯 2. Jeden warunek na test (KISS)

Każdy test powinien sprawdzać jeden warunek. Nie łącz wiele asercji w jednym teście! 

// ❌ ŹLE - zbyt wiele warunków
@Test
public void testCalculator() {
    assertEquals(8, calculator.add(5, 3));
    assertEquals(2, calculator.subtract(5, 3));
    assertEquals(15, calculator.multiply(5, 3));
    assertEquals(1, calculator.divide(5, 3));
}

// ✅ DOBRZE - oddzielne testy
@Test
public void testAdd() {
    assertEquals(8, calculator.add(5, 3));
}

@Test
public void testSubtract() {
    assertEquals(2, calculator.subtract(5, 3));
}

🛡️ 3. Unikaj magicznych liczb

Używaj named constants zamiast magicznych liczb i stringów. 

// ❌ ŹLE - magiczne liczby
@Test
public void testAdd() {
    assertEquals(8, calculator.add(5, 3));
}

// ✅ DOBRZE - named constants
@Test
public void testAdd() {
    final int FIRST_NUMBER = 5;
    final int SECOND_NUMBER = 3;
    final int EXPECTED_RESULT = 8;
    
    assertEquals(EXPECTED_RESULT, calculator.add(FIRST_NUMBER, SECOND_NUMBER));
}

🔄 4. Testy powinny być niezależne

Kolejność uruchomienia testów nie powinna mieć znaczenia. Każdy test powinien być niezależnym. 

// ❌ ŹLE - testy zależą od siebie
private static int counter = 0;

@Test
public void testFirst() {
    counter++;
    assertEquals(1, counter);
}

@Test
public void testSecond() {
    counter++;
    assertEquals(2, counter);  // Może się nie powieść jeśli testSecond uruchomi się pierwszy!
}

// ✅ DOBRZE - @BeforeEach resetuje stan
private int counter;

@BeforeEach
public void setUp() {
    counter = 0;
}

@Test
public void testIncrement() {
    counter++;
    assertEquals(1, counter);
}

💬 5. Dodaj wiadomości do asercji

Wiadomość pomaga zrozumieć, dlaczego test się nie powiedzie. 

// ✅ DOBRZE
assertEquals(8, calculator.add(5, 3), 
    "5 + 3 powinno równać się 8");

// Jeśli test się nie powiedzie, zobaczymy wiadomość!

🚀 6. Testuj edge cases

Pamiętaj o przypadkach granicznych i ekstremalnych:

  • Zero
  • Liczby ujemne
  • Null
  • Puste collections
  • Bardzo duże wartości

❌ 7. Nie testuj implementacji, testuj zachowanie

Testuj CO kod robi, a nie JAK to robi. 

// ❌ ŹLE - testowanie implementacji
@Test
public void testAdd() {
    // Testujemy wewnętrzną strukturę
    assertTrue(calculator.getInternalState().contains(result));
}

// ✅ DOBRZE - testowanie zachowania
@Test
public void testAdd() {
    assertEquals(8, calculator.add(5, 3));
}

8. Jak uruchomić testy?

🖥️ Wiersz poleceń (CLI)

cd examples/01-unit-tests-java

# Uruchom wszystkie testy
mvn test

# Uruchom tylko CalculatorTest
mvn test -Dtest=CalculatorTest

# Uruchom konkretny test
mvn test -Dtest=CalculatorTest#testAdd_PositiveNumbers

💡 IntelliJ IDEA

Metoda 1: Uruchom całą klasę testową

  1. Otwórz plik CalculatorTest.java
  2. Kliknij zielony play ▶️ obok nazwy klasy
  3. Wybierz "Run 'CalculatorTest'"

Metoda 2: Uruchom jeden test

  1. Kliknij na metodę testową (np. testAdd_PositiveNumbers)
  2. Naciśnij Ctrl+Shift+F10 (Windows) lub Cmd+Shift+R (Mac)
  3. Lub right-click → Run

Wynik w IntelliJ:

✅ Green bar = Wszystkie testy przeszły
❌ Red bar = Jakiś test się nie powiedzie

🔍 VS Code

Po zainstalowaniu "Extension Pack for Java":

  1. Nad każdą metodą testową pojawi się "Run" i "Debug"
  2. Kliknij "Run" aby uruchomić test
  3. Wynik pojawi się w panelu "Test Explorer"

9. Projekt Maven

Projekt zawiera przykładowy kod do testowania. Możesz go używać jako szablonu dla swoich testów.

📦 Struktura projektu

01-unit-tests-java/
├── src/
│   ├── main/java/com/example/
│   │   ├── Calculator.java        ← Kod do testowania
│   │   └── StringUtils.java       ← Więcej kodu
│   └── test/java/com/example/
│       ├── CalculatorTest.java    ← Testy (gotowe)
│       └── StringUtilsTest.java   ← Testy (TODO do uzupełnienia)
└── pom.xml                         ← Konfiguracja Maven

🧪 Metody do testowania w Calculator:

  • add(a, b) - dodawanie
  • subtract(a, b) - odejmowanie
  • multiply(a, b) - mnożenie
  • divide(a, b) - dzielenie (rzuca ArithmeticException przy dzieleniu przez 0!)
  • isEven(n) - sprawdzenie parzystości
  • isPositive(n) - sprawdzenie czy dodatnia

📝 Metody do testowania w StringUtils:

  • reverse(text) - odwrócenie stringa
  • capitalize(text) - kapitalizacja
  • isPalindrome(text) - sprawdzenie palindromu
  • repeat(text, count) - powtórzenie
  • isBlank(text) - sprawdzenie białych znaków

👉 Przejdź do: Projekt Maven - 01-unit-tests-java/

W projekcie znajduje się szczegółowa instrukcja, jak otwierać w IDE i jak uzupełniać brakujące testy.

10. Podsumowanie

Główne idee tego wykładu:

  1. Testy jednostkowe to automatyczne procedury sprawdzające czy kod zachowuje się poprawnie
  2. AAA Pattern (Arrange, Act, Assert) to standardowa struktura testu
  3. JUnit 5 to nowoczesny framework z anotacjami jak @Test, @BeforeEach
  4. Asercje (assertEquals, assertTrue, assertThrows) sprawdzają warunki
  5. Edge cases - testuj graniczne i ekstremalne sytuacje
  6. Best Practices - jedna asercja na test, dobre nazwy, niezależne testy
  7. Wynik: Bardziej niezawodny, łatwiejszy do utrzymania kod

💡 Pamiętaj: Testy nie są dodatkiem do programowania - to nieodłączna część budowania dobrego oprogramowania!
