@PostMapping("/schedule")
ResponseEntity<?> schedule(@RequestBody Request request) {
    var event = entityManager.find(ProgramEventEntity.class, request.eventId());

W domenie konwentu: kontroler nie powinien decydować, czy sala jest wolna. Jest tylko recepcjonistą — odbiera żądanie HTTP i tłumaczy je na polecenie zrozumiałe dla aplikacji.

1. Heksagon: granica decyzji biznesowych

Architektura heksagonalna (Ports & Adapters) oddziela wnętrze aplikacji od technologicznych sposobów komunikacji. Kształt nie ma znaczenia; znaczenie ma granica i kierunek zależności.

Domena

Agregaty, Value Objects i reguły. Nie zna transportu ani persystencji.

Aplikacja

Orkiestruje: pobierz, wywołaj zachowanie, zapisz, powiadom.

Adaptery

Tłumaczą HTTP, SQL lub komunikat na język portów i z powrotem.

3. Przypadek użycia: orkiestracja, nie reguły

public ScheduleResult handle(ScheduleProgramEventCommand command) {
    DaySchedule schedule = schedules.findByDate(command.date())
            .orElseGet(() -> DaySchedule.empty(command.date()));
    ProgramEventScheduled event = schedule.schedule(
            command.eventId(), command.roomId(), command.timeSlot());
    schedules.save(schedule);
    notifier.programEventScheduled(event);
    return ScheduleResult.scheduled(event);
}

Warstwa aplikacyjna wyznacza kolejność kroków. Reguła „sala nie może mieć dwóch wydarzeń jednocześnie” pozostaje w DaySchedule, bo jest prawdą domenową.

Test odpowiedzialności: język eksperta → domena; przebieg przypadku użycia → aplikacja; biblioteka lub protokół → adapter.

4. Adapter tłumaczy dwa światy

REST — adapter wejściowy

@PostMapping("/api/schedule")
ResponseEntity<ScheduleResponse> schedule(@RequestBody ScheduleRequest request) {
    var result = useCase.handle(request.toCommand());
    return ResponseEntity.status(201).body(ScheduleResponse.from(result));
}

Pamięć — adapter wyjściowy

public final class InMemoryDayScheduleRepository
        implements DayScheduleRepository {
    private final Map<LocalDate, DaySchedule> schedules = new HashMap<>();
    public Optional<DaySchedule> findByDate(LocalDate date) {
        return Optional.ofNullable(schedules.get(date));
    }
    public void save(DaySchedule schedule) {
        schedules.put(schedule.date(), schedule);
    }
}

5. Zależności wskazują do środka

6. Onion Architecture — architektura warstwowa w DDD

Onion Architecture pokazuje system jako współśrodkowe warstwy. Im bliżej środka, tym bardziej stabilne są pojęcia i reguły biznesowe. Zależności kodu zawsze wskazują do wnętrza: infrastruktura zna aplikację, aplikacja zna domenę, ale domena nie zna żadnej z nich.

1 // Model domenowy

DaySchedule, ProgramEvent, RoomId i TimeSlot wyrażają język konwentu. Agregat nie pozwala zaplanować dwóch wydarzeń w tej samej sali i czasie.

2 // Usługi domenowe

Umieszczamy tu regułę tylko wtedy, gdy nie pasuje naturalnie do jednej encji lub agregatu, np. politykę przydziału sal uwzględniającą pojemność i wyposażenie.

3 // Warstwa aplikacji

ScheduleProgramEvent realizuje scenariusz organizatora: pobiera plan, wywołuje zachowanie domeny, zapisuje wynik i zleca powiadomienie uczestników.

4 // Infrastruktura i interfejsy

Kontroler REST, panel, import CSV, JPA i SMTP są wymiennymi szczegółami. Tłumaczą dane, lecz nie decydują, czy sala jest dostępna.

Onion a Hexagonal: obie architektury chronią domenę i odwracają zależności. Heksagon podkreśla porty i adaptery na granicy, a cebula — kolejne pierścienie odpowiedzialności wokół modelu domenowego.

  3. Zastąp adapter in-memory własną implementacją.

Podsumowanie

  • Heksagon chroni decyzje biznesowe przed szczegółami technicznymi.
  • Port wejściowy nazywa możliwości, wyjściowy — potrzeby systemu.
  • Adapter jest tłumaczem, a nie miejscem na reguły.
  • Zależności źródłowe kierują się do środka.
