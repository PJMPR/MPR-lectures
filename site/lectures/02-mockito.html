Hamcrest + Mockito

CZYTELNE ASERCJE // IZOLACJA ZALEŻNOŚCI // TESTY ZACHOWANIA

Jak testować logikę biznesową bez bazy danych, systemu płatności i poczty, a przy tym otrzymywać komunikaty błędów, które rzeczywiście pomagają.

Spis treści

  1. Co sprawdza dobry test jednostkowy
  2. Hamcrest i język matcherów
  3. Mockito i izolacja zależności
  4. Weryfikacja interakcji i argumentów
  5. Typowe błędy
  6. Projekt demonstracyjny i zadania

1. Cele wykładu

Po zajęciach student potrafi:

  • budować czytelne asercje Hamcrest dla wartości, obiektów i kolekcji,
  • odróżnić mock, stub, fake i spy,
  • izolować zależności klasy za pomocą Mockito,
  • sprawdzać wynik oraz istotne efekty uboczne,
  • rozpoznać test kruchy i nadmiernie związany z implementacją.

2. Stan i zachowanie

Test może obserwować dwa rodzaje efektów.

RodzajPytaniePrzykład
StanCo zwrócił lub zmienił kod?Zamówienie ma status PAID.
ZachowanieZ kim i jak kod się komunikował?Repozytorium zapisało zamówienie dokładnie raz.

Hamcrest dobrze opisuje stan. Mockito pozwala kontrolować i obserwować współpracowników testowanej klasy.

3. Duble testowe

DubelRolaPrzykład

Mockito technicznie tworzy mocki, ale ten sam obiekt często pełni w teście rolę stuba i mocka.

4. Hamcrest: asercja jako zdanie

import static org.hamcrest.MatcherAssert.assertThat;
import static org.hamcrest.Matchers.*;

assertThat(order.getStatus(), is(OrderStatus.PAID));
assertThat(order.getTotal(), comparesEqualTo(new BigDecimal("149.90")));
assertThat(order.getCustomerEmail(), allOf(
        containsString("@"),
        endsWith("example.com")
));

Matcher opisuje oczekiwanie i potrafi wyjaśnić niedopasowanie. Błąd pokazuje oczekiwaną regułę oraz rzeczywistą wartość.

5. Konfiguracja Hamcrest

<dependency>
    <groupId>org.hamcrest</groupId>
    <artifactId>hamcrest</artifactId>
    <version>3.0</version>
    <scope>test</scope>
</dependency>

W JUnit 5 używamy org.hamcrest.MatcherAssert.assertThat. Hamcrest może działać obok asercji JUnit, więc migracja nie wymaga przepisywania całego zestawu testów.

7. Kolejność tylko wtedy, gdy wymaga tego domena

List<String> ids = List.of("ORD-101", "ORD-102", "ORD-103");

assertThat(ids, contains("ORD-101", "ORD-102", "ORD-103"));
assertThat(ids, containsInAnyOrder(
        "ORD-103", "ORD-101", "ORD-102"));
assertThat(ids, everyItem(startsWith("ORD-")));

Zbyt dokładna asercja tworzy fałszywe alarmy podczas refaktoryzacji. Sprawdzaj tylko cechę, którą opisuje nazwa testu.

8. Własny matcher domenowy

public final class PaidOrderMatcher
        extends TypeSafeDiagnosingMatcher<Order> {

    protected boolean matchesSafely(Order order, Description mismatch) {
        if (order.getStatus() != OrderStatus.PAID) {
            mismatch.appendText("status was ")
                    .appendValue(order.getStatus());
            return false;
        }
        return true;
    }

    public void describeTo(Description description) {
        description.appendText("a paid order");
    }
}

assertThat(order, is(paidOrderWithId("ORD-101"))); wyraża regułę biznesową zamiast struktury obiektu.

9. Mockito: testowana klasa i jej granice

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock OrderRepository repository;
    @Mock PaymentGateway paymentGateway;
    @Mock NotificationService notificationService;

    @InjectMocks OrderService service;
}

@Mock tworzy kontrolowane zależności. @InjectMocks buduje testowany obiekt i przekazuje mu mocki. Konstruktor nadal pozostaje najlepszym sposobem wstrzykiwania zależności w kodzie produkcyjnym.

10. Konfiguracja Mockito z JUnit 5

<dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-junit-jupiter</artifactId>
    <version>5.24.0</version>
    <scope>test</scope>
</dependency>

Mockito 5 wymaga co najmniej Java 11. Rozszerzenie JUnit inicjalizuje adnotacje i włącza kontrolę zbędnego stubowania.

11. Stubbing: przygotowanie odpowiedzi

when(paymentGateway.charge(
        "ORD-101", new BigDecimal("149.90")))
    .thenReturn(PaymentResult.approved("TX-777"));

when(repository.save(any(Order.class)))
    .thenAnswer(invocation -> invocation.getArgument(0));

Stub opisuje warunek wejściowy i odpowiedź zależności. Brak konfiguracji daje wartości domyślne, między innymi null, 0, false lub pustą kolekcję zależnie od typu.

12. Matchery argumentów Mockito

when(paymentGateway.charge(
        eq("ORD-102"),
        any(BigDecimal.class)))
    .thenReturn(PaymentResult.declined());

Jeżeli jeden argument używa matchera Mockito, wszystkie argumenty w tym wywołaniu także muszą używać matcherów. eq, any i argThat pochodzą z Mockito, a nie z Hamcrest.

13. Weryfikacja ważnych interakcji

verify(repository).save(order);
verify(notificationService)
    .sendOrderConfirmation("ada@example.com", "ORD-101");

verify(repository, never()).save(any());
verifyNoInteractions(notificationService);

Weryfikuj efekty widoczne na granicy systemu. Nie sprawdzaj każdego pomocniczego wywołania tylko dlatego, że Mockito to umożliwia.

14. ArgumentCaptor: co opuściło testowaną klasę

ArgumentCaptor<Order> captor =
        ArgumentCaptor.forClass(Order.class);

verify(repository).save(captor.capture());
assertThat(captor.getValue(),
        is(paidOrderWithId("ORD-101")));

Captor przydaje się, gdy kod tworzy lub modyfikuje argument przed przekazaniem go dalej. Do prostego porównania wystarczy zwykle eq.

15. Kolejność interakcji

InOrder sequence = inOrder(
        paymentGateway, repository, notificationService);

sequence.verify(paymentGateway).charge(any(), any());
sequence.verify(repository).save(order);
sequence.verify(notificationService)
        .sendOrderConfirmation(any(), any());

InOrder stosuj wyłącznie wtedy, gdy kolejność ma znaczenie biznesowe. W przeciwnym razie test utrwali przypadkowy szczegół implementacji.

16. Ścieżka błędu

when(paymentGateway.charge(any(), any()))
    .thenReturn(PaymentResult.declined());

PaymentRejectedException exception = assertThrows(
    PaymentRejectedException.class,
    () -> service.placeOrder(order));

assertThat(exception.getMessage(),
    is("Payment rejected for order ORD-102"));
verify(repository, never()).save(any());

Dobry test błędu sprawdza wyjątek i brak niedozwolonych efektów ubocznych.

17. Metody void i wyjątki

doThrow(new MailServerException())
    .when(notificationService)
    .sendOrderConfirmation(any(), any());

doNothing()
    .when(notificationService)
    .sendOrderConfirmation(any(), any());

Rodzina doReturn, doThrow i doAnswer obsługuje metody void. Jest także bezpieczniejsza podczas stubowania spy, ponieważ nie wywołuje prawdziwej metody w fazie Arrange.

18. Spy: prawdziwy obiekt pod obserwacją

List<String> auditLog = spy(new ArrayList<>());
auditLog.add("payment approved");

assertThat(auditLog, contains("payment approved"));
verify(auditLog).add("payment approved");

doReturn(42).when(auditLog).size();

Spy domyślnie uruchamia prawdziwy kod. Korzystaj z niego oszczędnie, ponieważ częściowe mockowanie często sygnalizuje klasę zbyt trudną do rozdzielenia.

20. Pełny scenariusz: zaakceptowana płatność

@Test
void placeOrder_paymentApproved_savesPaidOrderAndSendsConfirmation() {
    Order order = order("ORD-101", "ada@example.com", "149.90");
    when(paymentGateway.charge("ORD-101", new BigDecimal("149.90")))
            .thenReturn(PaymentResult.approved("TX-777"));
    when(repository.save(any(Order.class)))
            .thenAnswer(invocation -> invocation.getArgument(0));

    Order result = service.placeOrder(order);

    assertThat(result, is(paidOrderWithId("ORD-101")));
    verify(repository).save(order);
    verify(notificationService)
            .sendOrderConfirmation("ada@example.com", "ORD-101");
}

22. Zadania laboratoryjne

  1. Dodaj rabat i sprawdź kwotę przekazaną do bramki płatności.
  2. Dodaj walidację adresu e-mail oraz test braku interakcji z zależnościami.
  3. Dodaj rezerwację towaru i zwolnienie rezerwacji po odrzuconej płatności.
  4. Napisz matcher orderWithTotal z opisem rzeczywistej wartości.

Każdy test powinien zachować układ Arrange, Act, Assert i mieć nazwę opisującą warunek oraz rezultat.

23. Podsumowanie

  • Hamcrest opisuje oczekiwany stan za pomocą komponowalnych matcherów.
  • Mockito odcina wolne lub niedeterministyczne zależności.
  • Stubbing przygotowuje odpowiedzi, a verification sprawdza ważne interakcje.
  • Najtrwalszy test sprawdza zachowanie publiczne i pomija nieistotne szczegóły implementacji.
