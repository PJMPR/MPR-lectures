DDD: taktyczne building blocks

IDENTITY // VALUE // BEHAVIOR

Przekładamy wiedzę o programie konwentu na model w kodzie. Rozróżniamy encje i Value Objects, bronimy niezmienników i uczymy się czytać diagram jak hipotezę — nie jak gotową prawdę.

Cele wykładu

Po spotkaniu student potrafi:

  • wybrać między encją a Value Object na podstawie znaczenia domenowego,
  • modelować tożsamość niezależnie od pól opisowych,
  • projektować niemutowalne Value Objects walidujące się przy tworzeniu,
  • umieszczać zachowanie tam, gdzie znajdują się dane i reguły,
  • rozpoznać model anemiczny i przenieść istotne decyzje do domeny,
  • odróżnić usługę domenową od aplikacyjnej, repozytorium od kolekcji i zdarzenie od komunikatu technicznego,
  • krytycznie analizować diagram klas zamiast mechanicznie go implementować.

2. Encja: ważna jest ciągłość

Czy to nadal ten sam panel?

ProgramistaPanel zmienił tytuł, salę, godzinę i jednego prowadzącego. To jeszcze ten sam punkt czy już sequel?
Ekspert domenowyTen sam. Uczestnicy nadal mają go w agendzie, a my śledzimy jego historię.
ProgramistaA jeśli tytuł pozostał ten sam, ale zgłoszono drugi panel?
Ekspert domenowyTo dwa punkty. „Wprowadzenie do smoków” nie jest numerem PESEL.

Wniosek modelowy: atrybuty nie definiują tożsamości. ProgramEventId definiuje ciągłość encji.

Encję rozpoznajemy po tożsamości i historii. Dwa obiekty o tych samych danych nie muszą oznaczać tego samego bytu; jeden obiekt pozostaje tym samym bytem mimo zmiany atrybutów.

Pytanie diagnostyczneJeśli „tak”
Czy śledzimy obiekt w czasie?Prawdopodobnie encja.
Czy dwie identycznie opisane sztuki mogą istnieć równocześnie?Potrzebna jest tożsamość.
Czy biznes mówi „ten sam”, „inny”, „poprzednia wersja”?Tożsamość jest częścią języka.
Czy zmiana opisowych pól zachowuje ciągłość?Równość nie może opierać się na tych polach.
public final class ProgramEvent {
    private final ProgramEventId id;
    private EventTitle title;
    private SpeakerStatus speakerStatus;
    private Schedule schedule;

    public void scheduleIn(RoomId roomId, TimeSlot timeSlot) {
        if (speakerStatus != SpeakerStatus.CONFIRMED)
            throw new SpeakerNotConfirmed(id);
        if (schedule != null) throw new AlreadyScheduled(id);
        this.schedule = new Schedule(roomId, timeSlot);
    }

    @Override public boolean equals(Object other) {
        return other instanceof ProgramEvent event && id.equals(event.id);
    }
}

Setter setRoom mówi o strukturze danych. scheduleIn mówi o intencji i daje miejsce na reguły.

3. Value Object: ważne jest znaczenie

Ten sam czas, żadnego dramatu

ProgramistaUtworzyłem dwa TimeSlot od 10:00 do 11:00. Który jest oryginałem?
Ekspert domenowyŻaden. Jeśli opisują ten sam przedział, są równymi wartościami.
ProgramistaCzyli nie potrzebują osobnych ID, historii i aktu urodzenia?
Ekspert domenowyNie. To godzina, nie członek rodziny królewskiej.

Wniosek modelowy: TimeSlot nie ma własnej tożsamości; porównujemy całą wartość i nie zmieniamy jej po utworzeniu.

Value Object opisuje cechę lub miarę. Nie ma odrębnej historii, porównujemy go po całej wartości, a zamiast modyfikacji tworzymy nowy egzemplarz.

public record TimeSlot(Instant start, Instant end) {
    public TimeSlot {
        Objects.requireNonNull(start);
        Objects.requireNonNull(end);
        if (!start.isBefore(end))
            throw new IllegalArgumentException("Start must be before end");
    }
    public boolean overlaps(TimeSlot other) {
        return start.isBefore(other.end) && other.start.isBefore(end);
    }
}

Nie istnieje „prawie poprawny” TimeSlot. Zachowanie overlaps znajduje się przy pojęciu przedziału.

4. Primitive obsession

String przyjmie wszystko

ProgramistaspeakerId i roomId są napisami. Funkcja przyjęła je odwrotnie i nikt nie protestował.
Ekspert domenowyCzyli sala A-17 prowadzi panel, a doktor Kowalski ma projektor i 120 miejsc?
ProgramistaKompilator twierdzi, że wszystko jest legalne.
Ekspert domenowyKompilator nie był na spotkaniu. Wyjaśnijmy mu domenę typami.

Wniosek modelowy: SpeakerId i RoomId zamieniają pomyłkę w błąd kompilacji.

// Argumenty łatwo zamienić; każdy String może zawierać śmieci.
schedule("42", "A-17", "2026-11-14T10:00", "2026-11-14T11:00");

// Typy pokazują role i ograniczają nielegalne wywołania.
schedule(new ProgramEventId("42"), new RoomId("A-17"),
         new TimeSlot(start, end));

6. Zachowanie bez jednego właściciela

Kto ma podjąć decyzję?

ProgramistaSprawdzanie sali umieścić w punkcie, sali czy VeryImportantBusinessHelper?
Ekspert domenowyDecyzja porównuje wymagania punktu z możliwościami sali. Żaden nie zna sam całej odpowiedzi.
ProgramistaCzyli usługa domenowa?
Ekspert domenowyTak, RoomSuitabilityPolicy. Nazwij ją po decyzji, nie po tym, jak ważnie ma wyglądać.

Wniosek modelowy: zachowanie bez naturalnego właściciela może trafić do nazwanej usługi domenowej — nie do klasy „od wszystkiego”.

public void handle(ScheduleProgramEvent command) {
    ProgramEvent event = events.findById(command.eventId())
        .orElseThrow(EventNotFound::new);
    event.scheduleIn(command.roomId(), command.timeSlot());
    events.save(event);
    eventPublisher.publish(new ProgramEventScheduled(
        event.id(), command.roomId(), command.timeSlot()));
}

Handler steruje przepływem. Reguła „czy wolno?” pozostaje w modelu. Transakcja i publikacja nie trafiają do encji.

7. Rozmowa zmienia model

Scena A — czy punkt to tylko dane?

ProgramistaMamy formularz: tytuł, sala, od, do. Zrobię klasę z getterami i setterami.
Ekspert domenowyNie każdą przyjętą propozycję od razu planujemy. Najpierw prowadzący musi ją potwierdzić.
ProgramistaCzyli pole confirmed=true?
Ekspert domenowyNiezupełnie. Potwierdzenie, zaplanowanie i wycofanie to trzy różne fakty.

Wniosek: pojawiają się stany i operacje confirmSpeaker, scheduleIn, withdraw, a nie jedno pole sterujące.

Scena B — konflikt nie zawsze blokuje

ProgramistaBlokujemy każdy konflikt czasu prowadzącego.
Ekspert domenowyW wersji roboczej tylko go oznaczamy. Blokujemy publikację. Wyjątkiem jest nagranie bez prowadzącego.
Programistaschedule może zwrócić ostrzeżenie, ale publish wymaga ich rozstrzygnięcia?
Ekspert domenowyTak. Koordynator musi widzieć problem, zamiast utracić szkic.

Wniosek: brak konfliktów jest warunkiem publikacji harmonogramu, a nie niezmiennikiem pojedynczego punktu. To prowadzi do wykładu 6 o agregatach.

Pytania pogłębiające: „Podaj ostatni nietypowy przypadek”, „Kiedy ostrzegamy, a kiedy zabraniamy?”, „Kto może zrobić wyjątek i czy podaje powód?”

Podsumowanie

  • Encja ma tożsamość i ciągłość; Value Object ma znaczenie wynikające z wartości.
  • Dobry model utrudnia utworzenie niepoprawnego stanu.
  • Zachowanie i dane reguły powinny być blisko siebie.
  • Usługa domenowa przechowuje bezpańską operację; aplikacyjna orkiestruje przypadek użycia.
  • Repozytorium odtwarza model, a zdarzenie domenowe nazywa istotny fakt.
  • Rozmowa i przykłady mają pierwszeństwo przed atrakcyjnym diagramem.
  • Reguły wielu punktów prowadzą do pytania o agregat — tematu wykładu 6.
