DDD: agregaty i granice spójności

CONSISTENCY // BOUNDARY // TRANSACTION

Harmonogram konwentu przestaje być zbiorem niezależnych rekordów. Wyznaczamy granicę, w której reguły muszą być prawdziwe natychmiast — także wtedy, gdy dwóch koordynatorów klika „Zapisz” jednocześnie.

Cele wykładu

Po spotkaniu student potrafi:

  • wyjaśnić agregat jako granicę spójności, a nie drzewo obiektów,
  • odróżnić Aggregate Root od encji wewnętrznej,
  • zapisać niezmienniki i dobrać najmniejszą granicę, która ich broni,
  • projektować repozytorium dla korzenia agregatu,
  • rozpoznać potrzebę optimistic locking,
  • koordynować agregaty przez ID, zdarzenia i eventual consistency.

1. Agregat: odpowiedź na pytanie o spójność

Agregat to klaster encji i Value Objects traktowany jako jedna jednostka zmiany. Granicę wyznaczają reguły, które muszą być prawdziwe po każdej operacji.

💬 Agregat w praktyce
Konwent: DaySchedule razem z wpisami agendy traktujemy jak jeden agregat, bo dopiero widząc wszystkie wpisy danego dnia możemy stwierdzić, czy nowa sala i godzina nie tworzą konfliktu. Nie chodzi o to, że klasy są połączone — chodzi o wspólnie chronioną regułę.
BOUNDARY

Granica

Wewnątrz: silna spójność i jedna transakcja. Na zewnątrz: ID i komunikaty.

ROOT

Aggregate Root

Jedyna brama modyfikacji wnętrza. Sprawdza reguły i ukrywa reprezentację.

INVARIANT

Niezmiennik

Zdanie prawdziwe przed i po każdej publicznej operacji agregatu.

💬 Root i niezmiennik
Konwent: koordynator nie modyfikuje samodzielnie pojedynczego AgendaEntry. Wywołuje DaySchedule.assign(...). Root ogląda pozostałe wpisy i pilnuje niezmiennika: po operacji żadna sala nie ma dwóch nakładających się wydarzeń.
Reguła dostępu: kod zewnętrzny nie pobiera AgendaEntry, by ustawić pole. Prosi DaySchedule o wykonanie intencji: assign, move albo cancel.

2. Jak wyznaczać granice

Nie zaczynaj od relacji w bazie. Zacznij od zdań wymagających atomowej ochrony.

zmniejsz granicę

Małe agregaty wygrywają domyślnie

„Cały konwent” jako jeden agregat chroniłby wszystko, ale każda zmiana blokowałaby wszystkich. Wybieramy DaySchedule: konflikty są atomowo rozstrzygane dla dnia, a sale i opisy wydarzeń pozostają osobnymi agregatami.

3. Referencje i repozytoria

Poza granicę prowadzi identyfikator

final class AgendaEntry {
    private final ProgramEventId eventId; // nie: ProgramEvent event
    private RoomId roomId;                // nie: Room room
    private TimeSlot slot;
}

ID zmniejsza graf ładowania, ujawnia granicę transakcji i nie pozwala przypadkiem zmienić obcego agregatu.

💬 Dlaczego tylko ID?
Konwent: wpis agendy potrzebuje informacji „wydarzenie event-42 odbywa się w sali A-17”. Nie musi ładować całego opisu prelekcji, biografii prowadzącego ani wyposażenia sali. Dzięki ID zmiana tytułu prelekcji nie staje się przypadkowo częścią transakcji układania harmonogramu.

Jedno repozytorium na korzeń

public interface DayScheduleRepository {
    Optional<DaySchedule> findById(DayScheduleId id);
    void save(DaySchedule schedule);
}
// Brak AgendaEntryRepository — wpis żyje wewnątrz harmonogramu.
Repozytorium nie jest DAO dla każdej tabeli. Odtwarza agregat wystarczający do sprawdzenia reguł i zapisuje go jako całość z punktu widzenia domeny.
💬 Dlaczego nie AgendaEntryRepository?
Konwent: gdyby można było osobno zapisać pojedynczy wpis, programista mógłby ominąć kontrolę konfliktów w DaySchedule. Repozytorium pobiera cały harmonogram dnia, root wykonuje decyzję, a następnie repozytorium zapisuje nowy stan agregatu.

4. Transakcja i współbieżność

Poprawna metoda domenowa nie wystarczy, jeśli dwie kopie agregatu mogą zostać zapisane bez wykrycia konfliktu. Pole version umożliwia optimistic locking.

UPDATE day_schedule
   SET payload = ?, version = version + 1
 WHERE id = ? AND version = ?;
-- 0 wierszy → ktoś zapisał nowszą wersję → konflikt
💬 Po co wersja?
Wersje v7 i v8: Ania i Bartek otwierają wersję 7. Ania zapisuje panel i tworzy v8. Próba Bartka oparta na v7 zostaje odrzucona, bo decyzja korzysta ze starego obrazu harmonogramu.
💬 Co pokazujemy użytkownikowi?
Ponowienie: system pobiera v8. Jeśli sala A została już zajęta przez panel Ani, Bartek wybiera inną salę lub godzinę. Automatyczne nadpisanie usunęłoby poprawną decyzję Ani.

Konflikt techniczny przekładamy na decyzję: ponowić operację na świeżym stanie albo poprosić użytkownika o rozstrzygnięcie. Ciche nadpisanie jest najgorszą opcją.

5. Wiele agregatów: zgoda na opóźnienie

Jedna komenda powinna zmieniać jeden agregat. Skutki w innych agregatach uruchamiamy przez zdarzenia domenowe.

💬 Jedna komenda, jeden agregat
Konwent: komenda „opublikuj harmonogram” zmienia stan DaySchedule. Nie powinna w tej samej transakcji modyfikować kont uczestników, systemu mailingowego i strony publicznej. Root emituje fakt SchedulePublished, a zainteresowane procesy reagują niezależnie.

💬 Natychmiastowa czy ostateczna?
Konwent: konflikt sali musi być wykryty przed zatwierdzeniem operacji — inaczej harmonogram od razu jest błędny. Natomiast publiczna strona może pokazać nową wersję sekundę później. To opóźnienie jest widoczne technicznie, ale nie łamie reguły biznesowej.

💬 Wszystkie pułapki w jednym scenariuszu
Konwent: wyobraźmy sobie Convention zawierający wszystkie dni, sale, wydarzenia, prowadzących i uczestników. Zmiana tytułu jednego panelu wymagałaby załadowania ogromnego grafu i mogłaby konfliktować ze zmianą sali w innym dniu. Publiczny setter wpisu ominąłby kontrolę root, a zapis bez wersji mógłby nadpisać pracę drugiego koordynatora.

7. Projekt przykładowy: Convention Schedule

Kompletny przykład jest w examples/06-ddd-aggregates: czysty Maven/Java 11, agregat DaySchedule, wpisy wewnętrzne, Value Object, zdarzenie publikacji, port repozytorium i testy.

💬 Jak czytać projekt?
Konwent: zacznij od testu odrzucającego dwa wydarzenia w tej samej sali. Następnie przejdź do DaySchedule.assign(...) i zobacz, że kolekcja wpisów jest prywatna. Kod infrastruktury nie podejmuje decyzji — tylko odtwarza i zapisuje root.
public void assign(String eventId, String roomId, TimeSlot slot) {
    requireDraft();
    boolean conflict = entries.stream().anyMatch(entry ->
        entry.roomId().equals(roomId) && entry.slot().overlaps(slot));
    if (conflict) throw new DomainRuleViolation("Room conflict");
    entries.add(new AgendaEntry(eventId, roomId, slot));
}

Otwórz opis projektu

Laboratorium

  1. Uruchom mvn test i przeczytaj testy jak specyfikację.
  2. Dodaj move(eventId, roomId, slot). Nie dopuść do konfliktu z samym sobą.
  3. Dodaj konflikt prowadzącego — najpierw zdecyduj, do którego agregatu należą dane.
  4. Zaimplementuj repozytorium in-memory wykrywające nieaktualną wersję.
  5. Zaprojektuj idempotentną reakcję na SchedulePublished.
Kryterium jakości: test pokazuje regułę biznesową. Jeśli musi znać kolejność setterów albo tabelę agenda_entry, granica przecieka.

Podsumowanie

  • Agregat to granica spójności i transakcji.
  • Root jest jedyną bramą modyfikacji wnętrza.
  • Niezmienniki prowadzą do granicy; konflikty zapisu pomagają ją zmniejszyć.
  • Między agregatami przekazujemy ID.
  • Repozytorium służy korzeniowi agregatu.
  • Optimistic locking chroni przed równoległym nadpisaniem.
  • Zdarzenia pozwalają uniknąć gigantycznej transakcji.
