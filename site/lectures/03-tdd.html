TDD: sterownik windy

RED // GREEN // REFACTOR

90-minutowy tutorial: 30 minut teorii i 60 minut implementacji jednej windy sterowanej testami z Hamcrest i Mockito.

Plan misji

  1. Dlaczego i kiedy TDD?
  2. Cykl Red–Green–Refactor
  3. Reguły pracy i pułapki
  4. Domena: jedna winda
  5. Scenariusz godzinnego live codingu
  6. Ściąga prowadzącego

Cele wykładu

Po zajęciach student potrafi:

  • przeprowadzić mały problem przez wielokrotne cykle Red–Green–Refactor,
  • wybrać najmniejszy kolejny przykład, który wnosi nową informację,
  • odróżnić implementację minimalną od docelowej architektury,
  • opisywać stan za pomocą Hamcrest, a granice systemu izolować za pomocą Mockito,
  • refaktoryzować wyłącznie przy zielonym zestawie testów.

1. TDD to informacja zwrotna, nie liczba testów

W TDD test jest pierwszym klientem projektowanego API. Zanim powstanie implementacja, zapisujemy konkretny przykład zachowania i obserwujemy jego porażkę. Dopiero potem tworzymy najmniejszy kod spełniający przykład.

Test-firstTest-Driven Development
Test zostaje napisany przed kodem.Każdy mały test wpływa na następny krok projektu.
Może opisywać od razu całą funkcję.Zakres rośnie przez konkretne przykłady.
Refaktoryzacja jest opcjonalna.Refaktoryzacja jest trzecią, obowiązkową fazą.

TDD nie gwarantuje dobrego projektu. Zapewnia natomiast krótką pętlę informacji zwrotnej, która pozwala bezpiecznie poprawiać decyzje projektowe.

2. Red–Green–Refactor

FazaPytanieWarunek zakończenia
REDJakie jedno nowe zachowanie jest potrzebne?Test nie przechodzi z właściwego powodu.
GREENJaki najmniejszy kod spełni przykład?Cały zestaw testów jest zielony.
REFACTORCo można uprościć bez zmiany zachowania?Kod jest czytelniejszy, a testy nadal przechodzą.

Najważniejszy rytm: uruchamiaj testy po każdej fazie. Czerwony test potwierdza, że test potrafi wykryć brak zachowania. Zielony zestaw daje bezpieczny moment na zmianę struktury.

3. Trzy prawa TDD

  1. Nie pisz kodu produkcyjnego, dopóki nie istnieje test, który nie przechodzi.
  2. Nie pisz więcej testu, niż potrzeba do uzyskania porażki — błąd kompilacji także jest porażką.
  3. Nie pisz więcej kodu produkcyjnego, niż potrzeba do przejścia bieżącego testu.

To ograniczenia treningowe, które wymuszają małe kroki. W praktyce wielkość kroku dobieramy do ryzyka i znajomości problemu.

4. Jak wybierać następny test

  • Zacznij od najprostszego przykładu bez wyjątków i efektów ubocznych.
  • Dodawaj po jednej osi zmienności: inny kierunek, błąd drzwi, przeciążenie, kolejka.
  • Nazwa testu ma opisywać warunek i obserwowalny rezultat.
  • Mockuj granice systemu, nie obiekty wartości ani prywatne szczegóły implementacji.
  • Nie przewiduj przyszłej architektury. Wydzielaj abstrakcję, gdy przykłady pokażą powtórzenie.

5. Hamcrest i Mockito w pętli TDD

assertThat(result.getStatus(), is(RideStatus.MOVING));
assertThat(controller.pendingFloors(), contains(7, 2));

verify(alarm).signal("OVERLOAD");
verifyNoInteractions(doors, motor);

Hamcrest opisuje zwrócony stan i kolejkę językiem zbliżonym do wymagania. Mockito sprawdza istotne komunikaty wysyłane do urządzeń. Test nie powinien odtwarzać każdej instrukcji metody.

9. Pierwszy cykl na żywo

RED — najpierw przykład

@Test
void floorAlreadyReached_doesNotStartAnyDevice() {
    when(floorSensor.currentFloor()).thenReturn(3);
    controller.requestFloor(3);

    RideResult result = controller.serveNext();

    assertThat(result.getStatus(), is(ALREADY_THERE));
    verifyNoInteractions(doors, motor, alarm);
}

Uruchom test i przeczytaj komunikat błędu. Dopiero teraz dodaj najprostszy kod obsługujący ten przypadek. Nie implementuj jeszcze jazdy.

GREEN — minimum

Dodaj kolejkę, pobierz aktualne piętro i zwróć wynik dla równych wartości. Zielony test nie oznacza końca pracy.

REFACTOR — nazwy i intencja

Sprawdź nazwy metod i usuń przypadkowe szczegóły. Uruchom cały zestaw testów przed rozpoczęciem następnego cyklu.

10. Test bezpieczeństwa: kolejność ma znaczenie

InOrder sequence = inOrder(doors, motor);
sequence.verify(doors).close();
sequence.verify(doors).isClosed();
sequence.verify(motor).move(Direction.UP, 7);

InOrder jest uzasadnione, ponieważ uruchomienie silnika przed zamknięciem drzwi byłoby błędem bezpieczeństwa. Nie używamy kolejności do utrwalania nieistotnych szczegółów.

12. Ściąga prowadzącego

  1. Powiedz na głos, jakie jedno zachowanie dodajesz.
  2. Napisz test i pokaż RED.
  3. Sprawdź, czy test przegrywa z oczekiwanego powodu.
  4. Napisz najmniejszą implementację i pokaż GREEN.
  5. Zapytaj studentów, co warto uprościć.
  6. Po refaktoryzacji ponownie uruchom wszystkie testy.
  7. Jeśli utkniesz, zmniejsz krok albo zajrzyj do katalogu solution.

Podsumowanie

  • Test poprzedza kod i definiuje następny mały krok.
  • Red potwierdza wartość testu, Green zamyka zachowanie, Refactor poprawia projekt.
  • Hamcrest opisuje rezultat, Mockito kontroluje granice sprzętowe.
  • Małe kroki są narzędziem zarządzania ryzykiem, nie celem samym w sobie.
