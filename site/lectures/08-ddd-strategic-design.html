1. Bounded Context: granica znaczenia

Bounded Context wyznacza obszar, w którym konkretny model i Ubiquitous Language zachowują spójne znaczenie. Po drugiej stronie granicy te same słowa mogą oznaczać coś innego.

i
Ta sama osoba, trzy reprezentacje. Modele mogą mieć wspólny identyfikator, ale nie muszą współdzielić klasy ani cyklu życia.

4. Context Map: mapa współpracy

Context Map pokazuje konteksty, odpowiedzialność za kontrakty oraz kierunek zależności modelu. To narzędzie rozmowy o organizacji systemu, nie diagram klas.

i
Strzałka pokazuje zależność. Rejestracja publikuje fakty, a odbiorcy wybierają sposób ochrony własnego modelu.

Wzorzec opisuje rzeczywistą relację zespołów i modeli. Sama technologia komunikacji nie wybiera relacji.

5.1 Partnership: wspólny sukces

Dwa konteksty współpracują jak partnerzy, gdy wartość pojawia się dopiero po skoordynowanej zmianie obu stron.

i
Koszt dopasowania. Program i Dostęp muszą wspólnie planować kontrakt, testy oraz wdrożenie. Nie wybieraj Partnership, jeżeli strony powinny rozwijać się niezależnie.

5.2 Customer / Supplier: negocjowany kontrakt

Upstream dostarcza informację, ale uwzględnia potrzeby downstreamu traktowanego jak klient.

i
Warunek dopasowania. Dostęp ma realny wpływ na kontrakt TicketActivated, lecz Rejestracja nadal jest jego właścicielem. Ryzykiem jest kolejka potrzeb wielu klientów po stronie dostawcy.

5.3 Conformist: świadoma zgodność

Downstream przyjmuje język i kontrakt upstreamu bez własnego tłumaczenia, gdy ochrona lokalnego modelu nie daje wystarczającej wartości.

i
To kompromis, nie błąd. Conformist jest rozsądny, gdy kontrakt jest stabilny, różnice semantyczne są małe, a stworzenie własnego modelu i translatora byłoby tylko kosztem.

5.4 Anti-Corruption Layer: ochrona modelu

Downstream zatrzymuje obcy język na granicy i tłumaczy tylko informacje potrzebne do własnych decyzji.

i
Granica wiedzy. ACL mapuje identyfikator i nazwę, ale świadomie odrzuca typ biletu. Kosztem jest kod mapujący i jego testy; korzyścią — autonomia modelu Programu.

5.5 Open Host Service: jedno wejście dla wielu

Upstream publikuje stabilny, ogólnodostępny interfejs zamiast utrzymywać osobną integrację dla każdego konsumenta.

i
Skala integracji. Jedno stabilne API ogranicza liczbę połączeń punkt–punkt. Upstream musi jednak zarządzać wersjami i nie może projektować kontraktu jako przypadkowej sumy życzeń wszystkich odbiorców.

5.6 Published Language: wspólny alfabet

Strony integracji opierają się na jawnie opisanym, wersjonowanym formacie, którego znaczenie nie zależy od kodu jednej aplikacji.

i
Published Language opisuje kontrakt. Może nim być JSON Schema, AsyncAPI lub inna uzgodniona specyfikacja. Często uzupełnia Open Host Service: jedno mówi, gdzie rozmawiamy, drugie — jakim językiem.

6. Anti-Corruption Layer: tłumaczenie na granicy

// Kontrakt Registration Context
public record AttendeeRegistered(
        String attendeeId, String displayName, String ticketType) {}

// Adapter po stronie Program Context
public final class RegistrationEventTranslator {
    public SpeakerCandidate translate(AttendeeRegistered event) {
        return new SpeakerCandidate(
                new ExternalPersonId(event.attendeeId()),
                DisplayName.of(event.displayName()));
    }
}

Translator pomija ticketType, bo Program nie podejmuje decyzji o typie biletu. Zmiana kontraktu zewnętrznego zatrzymuje się na granicy.

Event-Carried State

Zdarzenie niesie dane potrzebne odbiorcy. Mniej odpytywania, większy kontrakt.

Notification

Odbiorca pobiera szczegóły po sygnale. Prostszy komunikat, większe sprzężenie czasowe.

Jawne API

Odbiorca pyta o aktualny stan. Dobre dla zapytań, słabsze podczas awarii.

8. Testy kontraktów i autonomii

@Test
void ignores_ticket_details_when_creating_speaker_candidate() {
    var event = new AttendeeRegistered("p-42", "Ada Nowak", "VIP");
    var candidate = translator.translate(event);
    assertEquals("p-42", candidate.externalPersonId().value());
    assertEquals("Ada Nowak", candidate.displayName().value());
}
  • test domeny sprawdza reguły wewnątrz kontekstu,
  • test ACL sprawdza semantyczne mapowanie,
  • test kontraktowy wykrywa niezgodność producenta i konsumenta,
  • test architektury pilnuje kierunku zależności.

Podsumowanie

  • Bounded Context wyznacza granicę obowiązywania modelu i języka.
  • Te same osoby i zdarzenia mogą mieć różne reprezentacje.
  • Context Map ujawnia kierunek zależności i relacje zespołów.
  • Anti-Corruption Layer chroni model przed semantyką dostawcy.
  • Granica modelu może działać w modularnym monolicie.
